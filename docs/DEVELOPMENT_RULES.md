# 晨的小助手 · 开发与交付规则

## 开始工作

开始任何开发前：

1. 读取当前 main 最新提交。
2. 读取 AI_HANDOFF 顶部当前状态。
3. 检查 Open PR、Draft PR 和明确 WIP 分支。
4. 若存在进行中工作，先检查实际代码、最新 commit、CI、未完成事项、与 main 的差异/冲突。
5. 不把历史分支自动视为当前开发。

## 判断优先级

明确进行中的 PR / 分支实际代码
>
当前 main
>
AI_HANDOFF
>
历史记录

## CI 与构建

涉及 workflow、CI 排障、Windows 构建、发布、部署前，必须重新检查当前实际基础设施。

Runner 注册成功不等于迁移完成；只有真实 workflow 成功执行后才可确认该环境可用。

禁止为了让 CI 通过：

- 删除测试
- 弱化测试
- 绕过兼容性或安全检查
- 修改测试掩盖真实问题

必须遵守现有 validation、stability gate、浏览器回归和兼容性要求。

## 长任务检查点

多文件、多轮修改、长时间测试、可能跨聊天窗口的任务：

- 尽早建立明确开发分支。
- 每完成独立阶段 commit + push。
- 未完成也可使用清晰 WIP commit。
- 较长任务可建立 Draft PR。
- 重要进度不得只存在聊天或本地未提交文件。

若中途停止，AI_HANDOFF 至少记录：用户最后需求、分支、PR、最新 commit、已完成、未完成、核心文件、测试状态、已知问题、下一步。

## PR

存在未合并 PR 时，必须检查：

- PR 基于哪个 main
- 修改范围
- 最新 commit
- CI / tests
- 是否冲突
- 是否已被后续代码替代
- 是否仍符合当前产品方向

再决定继续、修复、合并或放弃。

## 生产环境

GitHub 与生产环境分开判断。

只有实际生产部署/发布完成并实际验证通过，才可更新生产基准。

仅能确认 health、版本号或 GitHub 状态时，不推断生产精确 commit。

## 历史代码治理

不得根据文件名、版本号或“看起来很旧”直接删除。

删除前检查 runtime owner、imports、includes、模板引用、JS/CSS、动态引用、tests、deploy scripts、workflows、Windows 更新链和文档。

推荐过程：

小批次处理 → 全仓库引用检查 → 确认无引用 → 删除 → 防回归测试 → 完整 CI / 浏览器验证 → 合并。

## AI_HANDOFF 更新触发

以下变化必须更新顶部当前状态：

- 创建/合并/放弃 PR
- 版本变化
- main 基准变化
- 生产部署/发布完成
- 生产基准变化
- 当前任务或下一步变化
- 新长期问题
- WIP / Draft PR
- CI / Runner / 构建环境变化


## 跨聊天交接的执行规则（2026-10-05）

1. 用户不需要每次提醒更新交接。独立阶段完成、出现阻塞、要求暂停/改方向、准备结束长任务、用户说“更新交接”时，执行助手必须提交交接检查点。
2. AI_HANDOFF顶部只保留一个当前快照：更新时间与时区、工作模式、最新用户要求、活动分支/PR、最后功能提交、完成事项、验证层级、未解决问题、环境路径、核心文件、唯一下一步。
3. 旧快照移到明确历史区，不连续堆叠多个“当前状态”；旧生产/版本记录保留历史身份，不冒充最新。
4. 暂停/讨论状态优先于代码进度；新聊天不得把已有WIP代码当继续开发授权。用户授权维护交接文件时可修改文档。
5. 活动分支未合并时同步默认分支的接管入口与当前模式/分支指针，让只读main的新聊天也能找到WIP。文档维护使用仅文档提交，不夹带功能合并/部署；分支受保护时走仅文档PR并说明尚未落到main。
6. 代码提交、CI、打包、用户安装、真实业务验收、生产部署独立记录。没有证据写“未知／待验证”。CI证据须对应明确head/run。
7. 不记录令牌、密码或客户敏感原始数据；复现只记录批次ID和必要错误。截图/结果用文字提炼，不能只依赖会失效的上传路径。
8. 最后功能提交使用可核对SHA；文档自己的提交SHA由GitHub查询，不预填不存在的自引用SHA。
9. 提交后从GitHub读回，检查：活动分支可找到、暂停状态清楚、下一步唯一、历史不覆盖当前、变更范围只有文档。最终回复给出固定入口链接和新聊天提示词。
10. 本机制由执行助手维护，不是平台自动同步保证；未提交到GitHub的聊天结论不能声称已持久保存。
