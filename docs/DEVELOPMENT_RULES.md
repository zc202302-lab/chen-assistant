# 晨的小助手 · 开发与交付规则

## 开始工作

开始任何开发前：

1. 读取当前 main 最新提交。
2. 读取 AI_HANDOFF 顶部当前状态。
3. 检查 Open PR、Draft PR 和明确 WIP 分支。
4. 若存在进行中工作，先检查实际代码、最新 commit、CI、未完成事项、与 main 的差异/冲突。
5. 不把历史分支自动视为当前开发。

## 判断优先级

明确进行中的 PR / 分支实际代码
>
当前 main
>
AI_HANDOFF
>

## CI 与构建

涉及 workflow、CI 排障、Windows 构建、发布、部署前，必须重新检查当前实际基础设施。

Runner 注册成功不等于迁移完成；只有真实 workflow 成功执行后才可确认该环境可用。

禁止为了让 CI 通过：

- 删除测试
- 弱化测试
- 绕过兼容性或安全检查
- 修改测试掩盖真实问题

必须遵守现有 validation、stability gate、浏览器回归和兼容性要求。

## 长任务检查点

多文件、多轮修改、长时间测试、可能跨聊天窗口的任务：

- 尽早建立明确开发分支。
- 每完成独立阶段 commit + push。
- 未完成也可使用清晰 WIP commit。
- 较长任务可建立 Draft PR。
- 重要进度不得只存在聊天或本地未提交文件。

若中途停止，AI_HANDOFF 至少记录：用户最后需求、分支、PR、最新 commit、已完成、未完成、核心文件、测试状态、已知问题、下一步。

## PR

存在未合并 PR 时，必须检查：

- PR 基于哪个 main
- 修改范围
- 最新 commit
- CI / tests
- 是否冲突
- 是否已被后续代码替代
- 是否仍符合当前产品方向

再决定继续、修复、合并或放弃。

## 生产环境

GitHub 与生产环境分开判断。

只有实际生产部署/发布完成并实际验证通过，才可更新生产基准。

仅能确认 health、版本号或 GitHub 状态时，不推断生产精确 commit。

## 历史代码治理

不得根据文件名、版本号或“看起来很旧”直接删除。

删除前检查 runtime owner、imports、includes、模板引用、JS/CSS、动态引用、tests、deploy scripts、workflows、Windows 更新链和文档。

推荐过程：

小批次处理 → 全仓库引用检查 → 确认无引用 → 删除 → 防回归测试 → 完整 CI / 浏览器验证 → 合并。

## AI_HANDOFF 更新触发

以下变化必须更新顶部当前状态：

- 创建/合并/放弃 PR
- 版本变化
- main 基准变化
- 生产部署/发布完成
- 生产基准变化
- 当前任务或下一步变化
- 新长期问题
- WIP / Draft PR
- CI / Runner / 构建环境变化
