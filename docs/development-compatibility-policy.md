# 晨的助手：新增功能兼容性审计规则

从 v1.4.1 起，本项目把“新增功能不能破坏已经确定的功能”作为强制开发规则，而不是开发完成后的可选检查。

## 核心原则

每次增加、修改、重构任何功能，都必须同时完成一次已有功能兼容性审计。新功能通过自己的测试并不代表可以合并；只有与已经确定的功能共同通过后，才允许进入 `main`。

## 每次变更必须完成的检查

1. **先确认影响范围**：列出本次修改涉及的页面、路由、数据库表、JavaScript、公共模板和跨模块依赖。
2. **审计已有确定功能**：尤其检查与本次改动共享页面、共享路由、共享状态、共享脚本和公共导航的已有能力。
3. **新增回归测试**：本次新需求至少有一条能够真实复现用户操作的 contract / browser acceptance / regression 测试；不能只检查元素是否存在。
4. **运行完整历史测试集**：现有生产回归、客户、缴费、导入导出、工作/生活隔离、搜索、资料、菜谱等测试都必须继续通过。
5. **不得为了“变绿”而削弱旧测试**：只有产品规则明确改变时才允许修改旧断言，并在 PR 中说明原规则、现规则和迁移原因。
6. **跨功能公共组件必须做真实交互测试**：例如返回上一级、搜索、底部导航、金额核对等，不能只验证 HTML 属性存在，至少要验证一次真实点击后的结果。
7. **数据状态必须验证“未修改项不受影响”**：对缴费核对、排序、批量编辑等局部操作，测试中必须同时断言被操作项发生预期变化、未操作项保持原状态。

## 合并门槛

PR 合并前必须同时满足：

- JavaScript / Python 基础语法检查通过；
- stability gate 通过；
- 历史 contract / regression / browser acceptance 全部通过；
- 本次新增的回归测试通过；
- PR 的“已有功能兼容性审计”清单完成。

只要任意一项失败，就先修复冲突或回归，不直接合并。

## 当前重点稳定功能

当前至少包括：工作/生活空间隔离、客户管理、缴费四步流程、金额编辑与核对、固定/变动缴费规则、TXT、Foxmail 发起缴费、客户模板、客户 Excel 导入导出、优惠、搜索、远程客户资料、菜谱与工具、顶部返回与底部导航。

后续一项功能一旦由用户确认并进入稳定使用，也自动加入“已有确定功能”，之后所有新开发都必须把它纳入兼容性审计。
