## 优先问题

### A1 高：中转表清空存在竞态，可能丢失下一批
位置：windows/cloud-assistant/member_add_agent.py:583–584（PR #128）。
先读取比较原表字节，再write_bytes清空，两步不具备原子性。另一端在比较返回后、清空前写入的新任务会被覆盖。write_bytes本身也会截断原文件，写入中断可能损坏永久表。
验证：在第二次read_bytes返回旧内容的窗口注入新批次，执行process后新批次被空表覆盖，输出 NEW_BATCH_LOST True。现有“newer_batch_is_not_cleared”测试只覆盖比较前更新，未覆盖这一窗口。
建议：定义生产端和消费端共同遵守的交接协议/锁，批次独立文件与确认；永久Excel入口保留，不能只用原子replace替换后就声称并发问题已解决。

### A2 高：搜索就绪与提交成功条件没有绑定当前业务操作
位置：member_add_agent.py:380、483–484及_submit。
搜索只要求任一检查上下文body含集团编号并等待两秒，不能证明刷新完成、唯一当前集团及成员页属于目标集团；旧页面或列表文字可能满足条件。提交成功匹配整个body的通用“操作成功”等文字，没有证明回执是本次号码提交产生的。
验证层级：代码逻辑确认；真实业务中的误判尚未复现，不能声称已发生错加或假成功。
建议：绑定当前集团身份、当前成员区域与本次提交回执，开始前记录状态并等待明确变化；不确定则暂停。此项未解决前不建议无人值守批量执行。

### A3 中：客户Excel整库导出会将文本当公式/链接
位置：app/v032_customer_exchange_routes.py:214、298、329、339（main）。
Workbook只有in_memory，通用ws.write写入用户资料与备注。以“=”开头的文本被xlsxwriter识别为公式，网址也可能自动变为链接。影响导出忠实性，打开时可能触发公式计算/外部资源行为，取决于表格软件策略。
验证：使用同样Workbook与write配置写入 =1+1，生成worksheet XML包含 <f>1+1</f>。未打开Excel，也未执行外部请求。
建议：禁用strings_to_formulas/strings_to_urls，文本字段write_string，金额等仍保持数值。work_lists.py和缴费导出已有相应防护，可统一模式。

### A4 中：手动单次后台更新失败后仍可能正常退出
位置：windows/cloud-assistant/sync_updates.ps1:85–87。
catch仅Write-Host，再因Once退出循环，没有明确失败退出码；背景入口隐藏窗口，调用方不能可靠辨认失败。超时文字还称“60秒后自动重试”，但Once实际不会重试。
验证层级：脚本控制流确认，未在Windows执行。
建议：写结构化状态并以非零码失败退出，手动更新完成/失败给可见反馈，文案遵守单次更新行为。

### A5 中：失败批次也永久去重，原样重发会静默跳过
位置：member_add_agent.py:540–542及失败结果写入逻辑。
任何结果JSON存在就按文件哈希跳过，不区分验证错误、搜索前失败、提交不确定和成功。即使完全未操作业务，也无法原样再次处理；process返回None没有说明原因。
建议：明确批次状态与用户确认的重试入口。提交结果不确定必须保持禁止自动重试；不能简单删除去重判断。

### A6 安全边界风险：离线更新校验完整性，未验证发布者身份
位置：windows/cloud-assistant/offline_update.py:35–63。
ZIP和SHA256都来自同一共享目录，可写该目录者可同时替换包与manifest，使更新器运行任意替代EXE。仅校验文件名及版本无法证明来自仓库可信构建。
验证层级：代码信任边界确认；未证明共享目录对不可信用户可写，未执行攻击包。
建议：核对目录权限；使用内置公钥验证签名manifest/构建包，限制降级。风险大小取决于实际共享目录写权限。
